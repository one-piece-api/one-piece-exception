# ADR-0002: Document the error contract in consumers' OpenAPI specs

## Context

`one-piece-user-service` and `one-piece-content-service` now publish an OpenAPI spec
generated by springdoc (ADR-0014 in `one-piece-user-service`). springdoc cannot infer the
error responses on its own: `ApplicationExceptionHandler` returns a plain `ProblemDetail`
with no `@ResponseStatus`, so without help every spec would list success responses only.
The error shape is this library's contract (ADR-0001), not either service's.

## Decision

This library ships `ProblemDetailOpenApiCustomizer`, a springdoc `OpenApiCustomizer` that
adds the `ProblemDetail`/`FieldViolation` schemas, shared `ClientError`/`ServerError`
`application/problem+json` responses, and a `4XX`/`5XX` reference to them on every
operation that doesn't already document one.
`ProblemDetailOpenApiAutoConfiguration` registers it only when springdoc is on the
classpath: springdoc is a `compileOnly` dependency, never forced onto a consumer.
Version bumped to 0.2.0.

## Alternatives considered

- **Each service describes the schema itself**: duplicates the contract in every service,
  where it can drift from what this library actually returns.
- **Per-status responses (400/404/409/...) per operation**: more precise, but the
  application exceptions an operation can throw aren't visible to springdoc; guessing them
  would make the spec wrong more often than a status-range response that is always true.

## Consequences

- A service using springdoc gets its error responses documented with no code of its own.
- Status ranges are less specific than exact codes. A service can still document an exact
  status on one operation, and the customizer leaves it untouched.
- 401/403 rejected by the Spring Security filter chain carry no body (see ADR-0001). The
  `4XX` description says so rather than hiding it.
